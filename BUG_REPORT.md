## BUG 1 — User message not persisted for auto-created sessions

**File:** `app/api/server.py`
**Lines:** 252–253
**Severity:** High — causes silent data loss in session history

```python
session_id = req.session_id or sessions.get_or_create()
if req.session_id:
    sessions.add_message(session_id, "user", req.text)
```

**Why it happens:** When the client does not supply a `session_id`, a new session is auto-created via `get_or_create()`, but the user message is **never written** to the session store. The caller (`/query` at line 320) then writes only the assistant response:

```python
if session_id:
    app.state.sessions.add_message(session_id, "assistant", result.text)
```

**Impact:**
- The session history has an assistant reply with no preceding user message.
- `maybe_compact()` builds summaries from incomplete history (missing user messages).
- On the next request using the returned `session_id`, `build_context()` misses the original user turn.

## BUG 3 — FAISS index rebuilt from scratch on every cache lookup

**File:** `app/cache/semantic_cache.py`
**Lines:** 72–77
**Severity:** Medium — O(n) rebuild per lookup, degrades with cache size

```python
if faiss_available():
    import faiss
    matrix = np.ascontiguousarray(
        np.asarray([r["embedding"] for r in self.records], dtype="float32")
    )
    index = faiss.IndexFlatIP(matrix.shape[1])
    index.add(matrix)
    scores, ids = index.search(...)
```

**Why it happens:** `semantic_get()` creates a new `IndexFlatIP`, copies all embeddings into it, and searches — on **every call**. The index should be built once when records are loaded and incrementally updated on `semantic_put()`.

**Impact:** For a cache with 10k+ entries, each semantic lookup pays the full index-build cost. This defeats the purpose of caching.

## BUG 4 — All document embeddings re-encoded on every RAG search (numpy fallback)

**File:** `app/rag/retriever.py`
**Lines:** 52–56
**Severity:** High — makes RAG unusably slow without FAISS

```python
# numpy fallback (no FAISS)
matrix = self.embedder.encode([r["text"] for r in self.records])
scores = matrix @ q[0]
```

**Why it happens:** When FAISS is unavailable, `_get_index()` raises `RuntimeError`, which the caller catches and falls through to the numpy path. This path re-encodes **every** document chunk from scratch on each query. For a document set with hundreds of chunks and a transformer embedder, this takes many seconds per query.

**Impact:** RAG queries are extremely slow when FAISS is not installed, and the pre-computed vectors from `build_index` (saved to `.npy`) are never loaded.

## BUG 6 — Missing fallback cascade in `execute_route`

**File:** `app/api/server.py`
**Lines:** 214–217
**Severity:** Medium — only `medium→small` fallback exists; `small`, `moe`, `large` have no local fallback

```python
if route == "medium":
    return run_local("small", prompt, max_tokens=req.max_tokens)
if not local_only and state_has_network() and route != "cloud":
    return run_cloud(prompt)
raise HTTPException(status_code=503, detail=str(exc))
```

**Why it happens:** The fallback logic only handles `route == "medium"` specifically. For:
- `route == "small"`: skips to cloud (or raises 503). No attempt to try `medium` (which might have a different failure mode).
- `route == "moe"` or `route == "large"`: skips to cloud (or raises 503). No attempt to fall back to `medium` or `small` locally first.

**Impact:** A transient failure on a small/local model immediately escalates to cloud (potentially costly or unavailable) instead of trying an intermediate local tier.

## BUG 12 — Session context includes stale user message on replacement

**File:** `app/api/server.py`
**Lines:** 256–258
**Severity:** Low — minor UX inconsistency

```python
messages, _ = sessions.build_context(session_id)
if messages and messages[-1]["role"] == "user":
    messages[-1] = {"role": "user", "content": req.text}
else:
    messages.append({"role": "user", "content": req.text})
```

**Why it happens:** `build_context` returns the last N raw messages from the DB. If the last message is a user turn (from a previous request that was stored), it is **replaced** in-memory with the current query. But the previous user message is **not** removed from the database. On the next `build_context` call, both the old and new user messages may appear in the context.

**Impact:** The model may see duplicate or contradictory user turns in its context window.
